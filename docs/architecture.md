# Architecture

`codex-plugin-dsh` is an external DSH bundle and Host plugin. It registers a single `LlmAdapter` route named `codex-app-server`; the existing DSH model directory and browser model-selection plugin discover the route without a Client plugin or a source patch.

## Ownership

DSH owns the persisted Session, selected route, prompt and tool assembly, outer Agent Loop, tool permissions and execution, transcript, and managed subprocess lifecycle. Codex App Server owns model discovery, native account authentication, thread context, model inference, and native image generation. The adapter translates provider messages and bridges App Server dynamic-tool requests back into the DSH loop.

The built-in DSH `subagent-codex` package is a separate capability: it exposes Codex as a delegated one-shot subagent tool. This plugin exposes Codex App Server as the primary LLM route for an ordinary DSH Session.

## Plugin Design

- **Plugin type:** External function plugin and `LlmAdapter` bundle.
- **Owning package:** `codex-plugin-dsh`.
- **Extension point:** The DSH LLM adapter stream and the existing DSH dynamic-tool loop.
- **Required services:** LLM registry, Sessions, Session Persistence, Subprocess, Attachments, Agents, and User Questions.
- **Optional services:** None.
- **Model-visible behavior:** One App Server turn can remain open while a DSH dynamic tool waits across a DSH turn boundary; that live continuation takes priority over checkpoint resolution. Otherwise an exact completed remote head resumes in place, while divergence forks and a missing thread rebuilds from DSH history.
- **Durable behavior:** The DSH Session Log retains the canonical assistant, tool-call, tool-result, and replay-checkpoint events. The sidecar thread registry is a repairable ownership/reference projection; auxiliary calls publish no replay state.
- **Lifecycle owner:** The adapter owns every managed App Server connection until completion, the resettable inactivity deadline, authoritative Session disposal, or plugin disposal. The deadline is suspended while App Server is waiting on DSH or a human.
- **Test entry path:** Unit stream tests, composition tests, and opt-in live App Server tests.
- **Distribution form:** Existing local DSH profile bundle.

## Model routing

The DSH Agent Loop constructs each generation request from the Session's selected provider and model, then sends it through `ctx.llm`. The LLM service selects the registered adapter; the loop does not contain a fixed DeepSeek or OpenAI HTTP call. With provider `codex-app-server`, this adapter sends local JSON-RPC over stdio to `codex app-server`. The App Server uses the Codex account managed by the CLI and performs its own backend requests.

A DSH default model only supplies the initial Session selection. It is not a second upstream provider for a Session that has explicitly selected a Codex model.

## Model discovery

For a catalog read, the adapter resolves the configured Codex executable through `ctx.subprocess`, starts a managed App Server process, performs `initialize`, checks `account/read`, and reads every `model/list` page. Provider and model metadata then flow through the ordinary `ctx.llm` catalog used by the existing composer selector. `prepareCall` freezes this resolved metadata and dispatch closure as required by DSH `0.1.1-rc.2`; stateful App Server turns explicitly disable host retries.

The successful catalog is cached for `modelCacheMs`. Discovery failures remain provider-local catalog errors, so another DSH provider stays usable.

## Turn lifecycle

For a new DSH model turn, the adapter resolves the live Session from `sessionId`, reads its working directory, and starts one managed App Server connection. The connection remains alive when App Server requests a DSH tool, so several DSH model steps can continue one App Server turn. A DSH `turn/end` is deliberately not treated as teardown: an interactive tool can suspend an outer DSH turn before its result is available, then resume through a later provider call. Startup is owned before the turn is published: `session/disposed` or plugin disposal aborts and awaits initialize/read/resume/fork/inject/turn-start work before closing every published turn, preventing late startup from escaping teardown. The retained connection otherwise closes after the App Server finishes, the owning `session/disposed` event fires, its resettable inactivity deadline expires, or the plugin disposes. The inactivity deadline is held while an inbound App Server JSON-RPC request waits on a DSH tool or human answer, preventing a legitimate long-running tool from being mistaken for an idle turn. The current provider-step abort signal still cancels setup and active streaming before a pending tool call; it does not shorten an already-pending dynamic-tool RPC. Each later tool-result step uses its own abort signal for attachment reads. Teardown also owns the child stdin error boundary: if an already-running inbound JSON-RPC handler settles after stdin has ended, the resulting late-write error is contained instead of escaping as an unhandled Host-process error.

A conversational provider step first checks for an active App Server turn retained by the same DSH Session. If one is waiting for a dynamic-tool result, continuation of that exact RPC takes priority over all replay-checkpoint logic and remains pinned to its original model and tool catalog. Concurrent startup and duplicate tool-result continuations are single-flight within the adapter process.

Without an active turn, a request with no App Server replay checkpoint starts a thread and registers the exact DSH `options.tools` catalog as an experimental `dsh` dynamic-tool namespace. The thread is persistent for a top-level Session and for persistent child-agent modes. A Session whose durable header says `origin: subagent` becomes ephemeral only when the first supported `subagent/descriptor` positively classifies it as `one-shot`; missing or unsupported descriptors fail closed to persistent. An ephemeral one-shot still owns a live App Server turn across DSH dynamic-tool steps, but it publishes no creation receipt or terminal replay state, so it never enters the persistent Codex sidebar or registry projection. For a same-session persistent checkpoint with the same tool signature, the adapter first calls `thread/read`; because `thread/resume` does not roll back remote state, it resumes the canonical thread only when the checkpoint turn is exactly the remote head and that head is `completed`. A failed/interrupted head, an externally appended turn, or any other divergence instead calls `thread/fork` with the last DSH-committed turn. If `thread/read` reports the thread missing, the adapter creates a new owned thread and reimports every representable item from durable DSH history. Codex CLI `0.148.0` cannot replace dynamic tools during `thread/fork` or `thread/resume`, so a changed signature or cross-session checkpoint also starts a new thread and reimports representable DSH history. DSH `compaction` and `session-title` purposes always use separate ephemeral threads with no dynamic tools, no user-question bridge, and no replay checkpoint; therefore they cannot consume or disturb a retained conversational turn for the same Session.

Completed history after the checkpoint is converted to Responses input items and inserted before the new turn. The current trailing user input becomes the `turn/start` input. Ordinary user text and images retain their native input forms; known non-user-shaped blocks inside synthetic DSH user context (for example, a subagent settlement notice carrying its child's final `reasoning`, `tool-call`, or nested `tool-result`) are recursively projected as explicitly labeled inert text plus inline images. A copied tool call is never imported as a Responses `function_call`, because it did not execute in the parent thread and would otherwise create a dangling call. Image references are verified through the DSH attachment service and encoded as inline data URLs, so App Server never depends on a DSH-local attachment path. Assistant-role reasoning blocks are intentionally skipped during re-import: the Responses backend cannot accept client-injected reasoning items (it requires server-generated encrypted content and rejects unpersisted items), and the summaries remain available in the DSH session log. Assistant images still cannot be imported losslessly and fail before the turn starts.

App Server agent-message notifications become DSH streaming text or reasoning blocks. App Server does not expose model context capacity in `model/list`; configured global/per-model capacities are therefore published until an authoritative token-usage notification reports a capacity for that model. Official `reasoning` items contribute only their public streamed summaries (`item/reasoning/summaryTextDelta`, with `item/reasoning/textDelta` accepted as a fallback) to DSH reasoning blocks; raw reasoning content is deliberately not imported. `turn/start` requests `summary: "concise"` so the model is asked to produce reasoning summaries; whether one is emitted remains the model's and account's choice. The resulting standard DSH chunks are persisted with the assistant message, so Source, replay, and transcript export retain the same public summary. Completed `imageGeneration` items are decoded, validated, and persisted through the DSH attachment service before becoming assistant image blocks. A successful `turn/completed` notification produces a DSH stop finish plus replay state. Token-usage notifications are converted to DSH usage fields, including cached input and reasoning tokens.

## DSH tool-loop bridge

The adapter accepts the exact `GenerateOptions.tools` list produced by DSH. It does not inspect `ctx.tools` or rebuild the catalog, so the model sees the same preset, scope, policy, and code-mode result that another DSH provider would receive.

An App Server `item/tool/call` request is held open. The adapter emits the call as a normal DSH tool-call block and finishes that provider step with `tool-calls`. The ordinary DSH Agent Loop logs the assistant message, validates and schedules the call through its Tool Runtime, applies permissions and hooks, and appends the correlated tool result. If an interactive tool pauses and closes the outer DSH turn, the pending App Server RPC remains retained under the adapter deadline. On the provider step that receives its result, the adapter answers that same JSON-RPC request and continues consuming notifications from the same App Server turn. This continuation is bound to the active App Server turn's original model and tool catalog, because DSH reassembles `GenerateOptions` at each tool step and a UI/provider selection may otherwise have changed meanwhile. The newer selection applies only after the enclosing App Server turn finishes.

DSH tool-result text and images map to App Server dynamic-tool output. Messages added by DSH after the tool result, including Tool Runtime `additionalContexts`, are sent with `turn/steer`. Multiple simultaneous App Server dynamic calls are serialized across DSH steps; no call is executed inside the adapter, and standard DSH tool events remain the only durable execution log.

## Thread registry and governance

The DSH Session Log is authoritative for committed checkpoints and reconstructable conversation history. The versioned sidecar registry at `registryPath` (default `~/.dsh/codex-plugin-dsh/thread-registry.json`) is only a repairable projection: it stores plugin creation receipts, Session-to-thread canonical/branch/pending bindings, and external lifecycle observations. Startup reconciliation scans durable Session events to rebuild bindings and reference counts. A log-discovered thread without a matching creation receipt remains unowned, so reconstruction can restore context without granting destructive authority. Atomic replacement protects healthy registry writes. Malformed storage is retained, marked unhealthy, and never overwritten; existing threads reconstructed only from DSH events remain unowned without a creation receipt.

Normal model routing performs no destructive lifecycle action on existing threads: start, read, resume, fork, and missing-thread rebuild never archive, unarchive, or delete them. Explicit management is fail-closed. Archive requires an unreleased Session binding, proven plugin ownership, at most one live DSH Session reference, no local retained or starting turn, and a fresh `thread/read` whose head is not `inProgress`. Restore requires the registry's own archived state and the same ownership receipt. Purge requires an explicit confirmation flag, prior release of every Session reference, a fresh zero reference count, proven ownership, and another remote-active read; deletion then marks the receipt and all projections deleted. Shared, unknown, active, already-deleted, or otherwise unproven threads are skipped or rejected.

Within one plugin process, reconciliation shares one in-flight promise. New App Server startup and explicit lifecycle mutation share an adapter fence; receipt/event/reconcile/management state changes share an ordered registry lock; per-Session and per-thread management operations are additionally serialized. Archive, unarchive, and delete persist a write-ahead intent before the remote RPC, then commit the sidecar projection. A final-write failure therefore leaves a restart-visible intent that the same operation ID can safely retry/resume. These are in-process single-flight guarantees only. The sidecar has no cross-process lock or transaction protocol, so multiple DSH Host processes must not concurrently manage the same registry or Codex thread set.

The legacy one-shot cleanup helper is deliberately a dry-run. It reads the durable child header and own event suffix, requires the supported one-shot descriptor, a terminal own turn, one exact non-deleted creation receipt, an unreleased and unshared registry reference, no management intent, an existing unpinned Codex thread, and then reports only identifiers and reason codes. It does not call lifecycle RPCs or write SQLite. `eligible_after_live_check` still requires the registry's process-local active fence and a fresh App Server `thread/read` at execution time. Title and prompt heuristics never enter the decision.

Persistent thread presentation is intentionally non-authoritative. The adapter derives a display name from the latest durable `session/title`, the first direct human message, or a durable subagent label, then uses App Server `thread/name/set`. Persistent child threads use `threadSection/list` / `threadSection/create` / `thread/section/move` to enter the configured custom section. These requests run on the already-owned App Server connection, are memoized per thread/section within the adapter process, and fail open: a protocol or UI-version mismatch records a presentation error but never fails the model turn. No SQLite file is written directly, and no presentation state is used as an ownership or deletion signal.

## App Server capability isolation

App Server runs with a read-only sandbox and `never` approval because environment actions belong to DSH Tool Runtime. Per-thread configuration disables shell, unified exec, Web search, multi-agent, Apps, Plugins, view-image, and every MCP server visible in the effective Codex configuration. Developer instructions restrict remaining action requests to the `dsh` namespace and distinguish the DSH Skill loader from Codex host skills. A DSH `skill` call may use only names advertised by the DSH skill catalog; native Codex image generation is invoked directly instead of attempting to load `imagegen` from DSH. Command, file-change, and permission approval requests fail closed if App Server still emits one.

Native image generation remains enabled intentionally. Its completed image item is persisted through the DSH attachment service and exposed as an assistant image without entering the DSH tool loop. MCP elicitation is declined. App Server interactive user input (`item/tool/requestUserInput`) is bridged to the DSH user-questions dialog whenever the session has a live agent; secret questions and agentless calls fail explicitly instead of being shown unmasked or guessed.

## Process portability

The configured executable is resolved in the subprocess provider's execution environment. POSIX binaries and native Windows executables run directly. A Windows `.cmd` or `.bat` npm shim runs through a resolved `cmd.exe`; the quoted shim path travels in a per-process environment variable, while the command tail remains fixed.

The implementation does not assume the DSH Host and App Server share the local machine. A future remote subprocess provider can serve the same plugin when it supplies the executable, workspace, environment, streams, and process-tree semantics in its execution world.
